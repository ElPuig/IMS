# Fixes:

## Reinforcement group students no longer invisible on the group's own form:
- Root cause: `ems.group` had two completely disconnected notions of "who belongs to this group" for `group_type == 'reinforcement'`. `reinforcement_student_ids` (a plain `Many2many`, populated only by hand-editing the group's own "Students" tab) was the only membership shown on a reinforcement group's form; `ems.enrollment` (the real, per-subject enrollment model that actually drives attendance templates and grade sessions, and the same mechanism used to add students to a `main` group) was never surfaced there at all, since the "Enrolled" tab (`enrollment_view_ids`) was hidden whenever `group_type != 'main'`.
- Reported by a teacher who enrolled students into a "Reforç Programació" reinforcement group from the student's own form: the enrollment showed up on the student's card but nowhere on the group's own form.
- Fix (confirmed with the developer: no production reinforcement group relies on `reinforcement_student_ids` as the sole record of membership, so no data migration is needed): removed `reinforcement_student_ids` entirely and its own "Students" tab; the "Enrolled" tab (`ems.enrollment`-backed) is now shown for both group types, making `ems.enrollment` the single, unambiguous source of truth for group membership regardless of `group_type`.
- `_archive_confirmation_message()`'s active-student count is now type-aware (`main_student_ids` for `main` groups, `enrolled_student_ids` for `reinforcement` groups) instead of summing two fields that used to be mutually-exclusive by group type.
- Updated `docs/en/developers/contacts/group.md`, `docs/en/developers/employees/working_schedule.md`, and the trilingual admin manuals (`docs/{en,ca,es}/admin/groups.md`) to describe the new, single membership mechanism.
- Regression tests updated/added in `tests/test_group.py` and the tour (`static/tests/tours/group_tour.js` + `tests/test_group_tour.py`) to exercise reinforcement membership via `ems.enrollment` instead of the removed field.
- Found and worked around an unrelated, pre-existing Odoo `TransactionCase` gotcha while fixing this: a computed field with no `@api.depends` (like `enrolled_student_ids`) can resolve to a stale, empty cached value if it's read once (even indirectly, e.g. by unrelated ORM machinery) before the `ems.enrollment` row it depends on is created within the same test method - `invalidate_recordset(['enrolled_student_ids'])` after creating the enrollment, right before the assertion, is the fix already established in this same test file for the sibling field `enrollment_view_ids`. Not a production risk (a real HTTP request always gets a fresh environment/cache), but worth knowing for future tests against either field.
