# What's new

## Re-link Google sign-in button on the employee form:
A staff member whose `res.users` record lost its OAuth data (`oauth_provider_id` / `oauth_uid` emptied by hand, a bad import or a partial restore) could no longer log in at all, and nothing in the UI could repair it. `auth_oauth` matches an incoming login exclusively by `(oauth_uid, oauth_provider_id)` and its signup fallback fails on an already-existing login, so Google authenticates the person correctly and Odoo still answers "Access Denied"; there is no e-mail-based fallback and no password reset that helps. The new **Re-link Google sign-in** header button resolves the numeric Google id again through the Directory API and hands it to the same `_ems_link_google_signin()` the account-creation paths already use, so there is a single implementation of the link itself. It never touches the Google Workspace account, and it never overwrites a link that is already in place. Found on a real teacher account; 15 of 60 active teacher/ASP employees with a linked user had no `oauth_uid` in the development database, so it is not an isolated case.

# Internal changes

## Repair button is driven by its own field, not by another Google account state:
`google_ws_state` deliberately keeps meaning "which mutually-exclusive account action applies", and the four buttons it drives are unchanged. The repair is governed instead by a separate non-stored computed boolean, `google_signin_missing` (`google_ws_state == 'active'` and the linked user has no `oauth_uid`), so it renders *next to* Suspend rather than replacing it - the account really is active and fully set up, only its sign-in link is broken, and hiding Suspend meanwhile would misrepresent it. The compute reads the user's OAuth field through `sudo()`, since an `hr.group_hr_user` who is not an Odoo administrator cannot read `res.users` OAuth fields and the button must still render for them.

## Google id lookup can now report its failures instead of swallowing them:
`_gw_google_user_id()` took no arguments and returned `False` for every failure - correct for the queue jobs and creation paths that call it, useless for a button a person is waiting on. It now takes `raise_on_error` (default `False`, so every existing caller keeps the silent behaviour) which reports dry-run mode, a missing corporate address and an API failure as distinct errors. It deliberately does not try to tell "no such account" from "account outside my scope": the service-account role is scoped to the managed OUs and Google answers 403, not 404, for anything outside them, so the message names both causes rather than guessing. An `oauth_uid` already claimed by a different user (the `auth_oauth` unique constraint) is reported naming that user, since the fix there is to clear the stale record first.

## Employee Google Workspace tour no longer reaches the real Google Workspace:
The tour test seeded its 'active' teacher with `action_create_ems_user()`, which resolves the Google id through the Directory API - with real service-account credentials configured and dry-run off, every run made a genuine (failing) call against the centre's live Workspace. The Google id is now patched for the whole test, and the outgoing SMTP transport is mocked class-wide as the chatter posts require. The tour itself gained a second 'active' teacher whose user has no OAuth data, and it presses the repair button in a real browser and asserts the button disappears while Suspend stays.
